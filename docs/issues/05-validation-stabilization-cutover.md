# 이슈 5. 과거 메일 검증·통합 안정화·운영 전환

## 목표

완성된 시스템에 과거 메일을 넣어 실제 데이터 기준으로 분류·추출·카드 결과를 검증하고, 장애 복구와 운영 절차까지 확인한 뒤 기존 풍멜이 관리에서 새 시스템으로 안전하게 전환한다.

이 이슈가 끝나면 사용자는 관리 UI에서 과거 메일 하나를 골라 전체 노드 흐름과 최종 Discord 카드 예상 결과를 확인하고, 실제 운영 전환 여부를 결정할 수 있어야 한다.

## 사용자 확인 결과물

- 수집된 과거 메일 목록과 증거 자료 보존 상태
- UI에서 선택한 메일의 수동 검증 실행 결과
- 노드별 입력·출력·소요 시간·실패 원인 추적 화면
- 실제 전송 없이 확인하는 Discord 카드 예상 결과와 기대값 비교 화면
- 카테고리별 회귀 테스트 및 AI 평가 결과
- 프로세스 재시작, Outbox 복구, DB 백업·복원 시연 결과
- 기존 시스템과 새 시스템의 병행 관찰 비교 결과
- 운영 전환 후 첫 실메일과 첫 시간별 갱신 결과

## 범위

### 1. 과거 메일 검증 데이터 수집기

- 프로젝트 개발 완료 후 별도 스크립트로 실행한다.
- Gmail 검색식, 날짜 범위, 최대 건수 또는 메시지 ID 목록으로 수집 대상을 선택할 수 있게 한다.
- `project_architecture.md` 3번 항목에 맞춰 다음 자료를 보존한다.
  - Gmail thread/message 메타데이터
  - 본문 원문과 정규화 본문
  - 첨부파일 메타데이터와 원본 파일
  - PDF·문서·이미지 추출 텍스트 및 OCR 결과
  - 원본과 파생 자료의 해시
  - 수집 시각과 파서 버전
- 동일 Gmail message ID와 원본 해시를 기준으로 중복 수집하지 않는다.
- 원본 검증 자료는 Git에서 제외하고 로컬 전용 디렉터리에 저장한다.
- 자동 테스트에 필요한 사례는 개인정보·회사 기밀을 제거한 작은 fixture로 별도 관리한다.
- 기존 풍멜이 관리 DB는 필요할 때 참고용으로만 읽으며, 새 운영 DB로 자동 이관하지 않는다.

### 2. UI 수동 검증 실행

- 관리 UI에서 수집된 메일 한 건을 선택해 검증 실행을 시작할 수 있게 한다.
- 검증 실행도 운영과 동일한 `mail_processing` 흐름과 동일한 노드 구현을 사용한다.
- 검증 실행은 아래 부작용을 기본 차단한다.
  - Gmail 라벨 변경 금지
  - 실제 Discord 삭제·전송 금지
  - 운영용 업무 건과 주문 데이터 변경 금지
- 검증 결과는 운영 실행과 분리된 `validation_runs`, `validation_results`로 저장한다.
- 한 메일은 검증에서도 한 번의 메일 처리 이벤트이자 최대 한 개의 업무 건 결과만 만든다.
- 화면에서 다음을 확인할 수 있게 한다.
  - 원문·첨부·OCR·추출 근거
  - AI 분류 및 구조화 결과
  - 품목명·업체 판별 근거와 경고
  - 카테고리 처리 결과
  - 주문서·재고·RW·SI 판단 결과가 있는 경우 그 근거
  - 최종 Discord 카드 미리보기
  - 노드별 성공·실패·재시도·소요 시간
- 사용자가 카테고리, 핵심 추출값, 최종 카드 기대값을 기록하고 실제값과 비교할 수 있게 한다.
- 검증 화면은 결과 확인용이며 운영 데이터나 프롬프트를 편집하는 기능은 넣지 않는다.

### 3. 회귀 테스트와 AI 평가 세트

- 기존 `pungmail_policy v3.56`, 관리 프로젝트의 테스트, 기존에 정확히 동작하던 공급사·품목 분류 사례를 회귀 기준으로 옮긴다.
- 다음 카테고리별 대표·경계 사례를 포함한다.
  - 발주
  - 샘플·자료·견적 복합 업무
  - 기타 확정 카테고리
  - 보류
- 다음 공통 경계 조건을 검증한다.
  - 동일 thread의 후속 메일이 기존 업무 건 하나를 갱신
  - 한 메일에 여러 품목·PO가 있어도 업무 건 하나로 유지
  - AI가 선택한 카테고리 분기만 실행되고 나머지 분기는 `SKIPPED`
  - 발주 분기에서 발주 근거 처리와 오더시트·재고 확인 노드가 각각 기록됨
  - 오더 분기에서 RW·SI DB 처리와 진행·완료 계산 노드가 각각 기록됨
  - 분류 실패, 필수값 누락, 첨부 파싱 실패 시 보류 카드 생성
  - 회사 품목의 유사명·중복 품목코드·규격 차이를 임의로 합치지 않음
  - 삭제 품목 제외와 `companyDisplayName` 표기
  - 주문서 전 품목 정확 일치 및 충분 재고 조건
  - RW/SI 다대다 배정과 양방향 조회
  - Discord 기존 메시지 삭제 후 최신 카드 재전송
- AI 평가는 고정 모델·고정 프롬프트 버전·고정 입력 자료를 기록해 재현할 수 있게 한다.
- 구조화 출력 스키마 통과율, 분류 일치율, 필수 필드 정확도, 보류 전환 정확도를 집계한다.
- 허용 기준을 넘지 못한 사례는 기대값, 실제값, 근거, 조치 상태를 UI에서 추적한다.

### 4. 통합·장애 복구 검증

- Gmail 중복 수신, API 시간 초과, AI 응답 오류, 문서 파싱 실패, Discord 삭제 성공 후 전송 실패, 프로세스 강제 종료를 재현한다.
- 모든 실패는 구조화 로그와 `workflow_runs`·`node_runs`·Outbox 상태로 추적 가능해야 한다.
- 재시작 후 미완료 실행과 `REPOST_PENDING` Outbox가 중복 카드 없이 복구되는지 확인한다.
- 오래된 시간별 갱신 결과가 최신 메일 처리 결과를 덮어쓰지 않는지 revision 조건으로 검증한다.
- 앱 DB와 Prefect DB를 각각 백업·복원하는 로컬 스크립트와 운영 절차를 만든다.
- SQLite 무결성 검사와 복원 후 핵심 레코드 수·최근 실행·Discord 매핑 검사를 자동화한다.
- 로그와 검증 자료에서 OAuth 토큰, API 키, 메일 주소 등 민감정보를 마스킹한다.
- 로컬 서버는 `localhost`에만 바인딩하고 외부 접속이 열리지 않았는지 점검한다.

### 5. 병행 관찰과 운영 전환

- 빈 새 DB로 시작하고 기존 풍멜이 관리 시스템과 DB는 그대로 보존한다.
- 병행 관찰 기간에는 새 시스템이 실제 Discord와 Gmail에 부작용을 만들지 않도록 전송·라벨 변경을 차단한다.
- 같은 메일 표본에 대해 기존 결과와 새 결과의 카테고리, 핵심 추출값, 업무 상태, 카드 내용을 비교한다.
- 차이가 의도된 새 설계 때문인지 결함인지 기록하고 미해결 치명 결함이 없어야 한다.
- 운영 전환 순서는 다음과 같다.
  1. 앱 DB와 Prefect DB 백업
  2. 기존 풍멜이 관리 프로세스 중지 확인
  3. 새 시스템의 Gmail·Discord 부작용 활성화
  4. 첫 실메일의 전체 흐름과 Discord 도착 확인
  5. 첫 `order_status_refresh` 실행과 변경 주문 카드 갱신 확인
- 롤백은 새 시스템을 중지하고 기존 시스템을 다시 시작하는 방식으로 수행한다.
- 자동 DB 병합이나 양쪽 시스템의 동시 Discord 쓰기는 허용하지 않는다.

  - 설치 및 최초 실행

  - 로컬 서비스 시작·중지·상태 확인
  - 보류·실패·Outbox 복구 확인
  - 과거 메일 수집과 수동 검증
  - DB 백업·복원
  - 버전 업그레이드와 마이그레이션
  - 운영 전환과 롤백
- Windows 로컬 환경에서 한 번에 서버와 worker를 시작하고 정상 종료할 수 있는 실행 도구를 제공한다.
- Python, Prefect, OpenAI SDK 등 모든 런타임 의존성은 정확한 버전으로 고정한다.

## 완료 조건

- [ ] 과거 메일을 선택적으로 수집하면 본문·첨부·OCR·추출 텍스트·해시가 누락 없이 저장된다.
- [ ] UI에서 메일 한 건을 선택해 운영과 같은 노드 흐름을 부작용 없이 실행하고 추적할 수 있다.
- [ ] 메일 하나가 여러 업무 건으로 분리되지 않으며, 후속 메일은 기존 업무 건 하나를 갱신한다.
- [ ] 실행 상세에서 선택된 카테고리 노드만 실행되고 다른 분기는 `SKIPPED`로 구분된다.
- [ ] 발주 실행에는 오더시트·재고 확인 노드가, 오더 실행에는 RW·SI DB 처리 노드가 명시적으로 남는다.
- [ ] 모든 유효 대상 메일이 확정 카테고리 또는 보류 카드 결과에 도달하는 테스트가 통과한다.
- [ ] 기존 정책·테스트의 필수 사례와 새 경계 조건 회귀 테스트가 통과한다.
- [ ] 주문서 정확 일치·충분 재고, RW/SI 다대다, 삭제 후 재전송 규칙이 통합 테스트에서 확인된다.
- [ ] Discord 삭제 성공 후 전송 실패와 프로세스 종료 상황에서 재시작 복구가 검증된다.
- [ ] 백업한 앱 DB와 Prefect DB를 복원하고 무결성 점검을 통과한다.
- [ ] 병행 관찰에서 발견된 치명 결함이 모두 해소되고 차이점이 승인된다.
- [ ] 기존 시스템을 중지한 뒤 첫 실메일이 Discord에 도착하고 첫 시간별 상태 갱신이 정상 완료된다.
- [ ] 운영 전환과 롤백 절차를 문서대로 한 번 이상 리허설한다.
